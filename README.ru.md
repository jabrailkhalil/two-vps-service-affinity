# Два VPS: разделяем сервисы, сохраняем резерв

Практическая схема для небольшого приложения: API и основная PostgreSQL работают
вместе на одном сервере. Почта, лендинг и независимые продукты — на втором. Там же
хранится пассивная реплика приложения для аварийного восстановления.

[English](README.md) · [Архитектура](docs/architecture.md) ·
[Эксплуатация](docs/operations.md) · [Измерения](docs/performance.md)

Проект вырос из работы над [clickngoal](https://goal.clickn.dev/). Здесь описана
схема, её ограничения и проверяемые примеры. Это не автоматический установщик.

Главная причина разделения: удалённый API, который несколько раз обращается к
базе на другом сервере, добавляет сетевую задержку к каждому этапу запроса.
В наших небольших замерах локальный SQL занимал около 0,3 мс, межсерверный —
35–45 мс. Свободный гигабитный канал сам по себе это не исправляет.

Если сервер дополнительных сервисов падает, приложение продолжает работать.
Если падает сервер приложения, резерв показывает уже полученные данные;
изменения временно недоступны. Без отдельного арбитра и проверенного отключения
старого владельца автоматически включать вторую запись опасно.

Два диска не становятся одним отказоустойчивым диском. Независимые файлы можно
распределить, но данные, необходимые после аварии, занимают место на обоих узлах.
Реплика повторяет удаление данных и не заменяет исторические резервные копии.

Примеры используют вымышленные адреса и домены. Настоящие ключи, IP серверов,
данные пользователей и служебные квитанции сюда не публикуются.
